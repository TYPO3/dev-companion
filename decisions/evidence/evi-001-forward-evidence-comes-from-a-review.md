# D-EVI-001 — Forward evidence comes from a review

**Only an open review that names the working context and the user's intent
counts as forward evidence. Everything that names a task shape is a targeted
contract case.**

The scenario suite described what the three audiences need. It then also served
as the evidence that an agent finds those needs on its own. Those are two
different tests, and one file shape hid it.

## Evidence

- Every one of the 32 prompts named its own subsystem, and several named the
  implementation. A status list with a refresh action, a carousel with inline
  children. The one recorded forward run, `EXT-04` on 2026-07-30, met all five
  criteria it stood against. It produced six defects none of them measured,
  which is what a prompt that already contains the answer buys. Five prompts
  also named one project on one machine, so nobody else could run them.

## Decided

- The suite splits. Three open forward reviews, site project, reusable
  extension, core patch, name the working context and the user's intent and
  nothing else. Only these get a record. Everything that names a task shape
  becomes a targeted contract case: still readable, still printable, never
  forward evidence. One case is one file, and an environment is a kind of
  working directory rather than someone's checkout.

## Wrong if

- Two consecutive review runs produce findings too diffuse to tie back to a
  requirement or a feedback. Then the broad prompt measures the model's taste
  rather than this server. Or nobody reads the contract cases any more because
  nothing schedules them, and the routing they hold rots while the three reviews
  stay green.

## Confirmed on 2026-08-02

The findings tie back. Thirteen requirements and five decisions name one of the
two reviews as their source. Each of the four runs read produced at least one
finding a stated rule made it find and one this repository could file. A
minority ties back to nothing and it is the same shape in both. A deployment
cluster, correct and anchored and this server's in no part. So the measure is
per run rather than per finding.

## Confirmed on 2026-08-02

The strongest thing available schedules the contract cases. All 36 name live
tests in their **Held by** line, and `composer ci` runs those tests on every
commit. `ScenariosTest::everyContractCaseNamesWhatHoldsIt` fails when a rename
takes a named test away. What nothing schedules is the read by hand that seven
of them fall back on where **Held by** says `not guarded`. Those are `CORE-04`,
`CORE-06`, `EXT-01`, `SITE-01`, `SITE-08`, `SKILL-07` and `SKILL-09`. Two of
those carry weight already. `D-EVI-002` rests on `SKILL-07` read by hand, and
`SKILL-09` says in as many words that it is what measures the rest. That residue
is the todo behind this read, not a correction to this entry.

## Since then

A cadence reads the residue rather than a count:
`todo/recurring/read-the-contract-cases-no-test-can-hold.md`, every 14 days. Two
of the seven wait on knowledge and on a decision, which the session-recurring
backlog already brings round. The other five wait on what a session does, which
no test here reaches. On the first read four stood and `SITE-01` did not. The
boundary it asks for stands in neither `covers` nor `doesNotCover`, which a
session queued. Rejected: each proxy held to a digest of the file it stands in.
That fires on the better trigger and is a build rather than a cadence.
