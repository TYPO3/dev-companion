# D-KNW-098 — Where a site nobody wrote came from is a subject this server owns

**Nothing below `knowledge/` says that TYPO3 writes a site configuration of its
own when somebody creates a page at the root.**

So an installation carries a site whose identifier appears in no file the
repository ships, on a base under a sub-path. The corpus offers a caller four
other reasons a root request answers 404. The feedback goes to the queue at
`normal`.

## Evidence

- Re-run on 2026-08-18 against the corpus as it is now. The feedback's own task
  reaches `site-base-collision` first, where the report says it reached
  `initial-content-references`. `D-KNW-097`'s statement changed which neighbour
  answers and not that the neighbour is the wrong mechanism.
- The mechanism named directly reaches nothing. `bin/cli hints:probe` on
  `"site created automatically when a page is added at pid 0 is_siteroot CreateSiteConfiguration"`
  matched no hint and returned the index. `CreateSiteConfiguration` and
  `autogenerated` occur nowhere below `knowledge/` or `skills/`.
- The provenance query gets a wrong answer rather than none.
  `"a site configuration nobody wrote exists with identifier autogenerated and the frontend answers 404 at the root"`
  returns `site-label-language`, `routing-request-handling` and
  `site-base-collision` — the last of which sends a caller looking for a second
  site that is not there.
- Every claim the feedback makes about TYPO3 holds on `.checkouts/14.3`.
  `CreateSiteConfiguration::generateSiteConfigurationForRootPage()` invents
  `autogenerated-<uid>-<md5 of uid>`. It passes `getSiteUrl()` plus
  `autogenerated-<uid>` as the base and `getSitePath()` under CLI. It calls
  `updateSlugForPage()` with an empty slug after the write, and holds
  `$allowedPageTypes` as a protected array of `DOKTYPE_DEFAULT`, `LINK` and
  `SHORTCUT`.
- The hook fires by default and a subclass is how an extension adds a doktype.
  Core's own `ext_localconf.php` registers it under
  `SC_OPTIONS['t3lib/class.t3lib_tcemain.php']['processDatamapClass']` on
  `.checkouts/12.4`, `13.4`, `14.3` and `main`, keyed by the class name. So an
  extension that registers a subclass under that same key replaces it, which is
  the route the feedback reports `t3g/blog` takes.
- The symptom cluster names four causes and this is a fifth.
  `typo3-development-installation` lists four lookups for a request that reached
  the wrong site or none. The `installation-operations` intent carries a
  sentence per cause, and `site-base-collision` and `initial-content-references`
  point at each other. None of them covers a base the core invented.
- `D-KNW-097` reached this feedback from the other side and named it as the same
  gap by a different mechanism. It left it its own card so the run that judges
  it could carry both.

## Decided

- Step 1a, taken on, and a todo rather than the spot. What the statement says
  about TYPO3 has to be read, which
  [`judging.rst`](../../documentation/records/judging.rst) puts on the todo's
  side of the line whatever its size.
- `normal` rather than the `low` the card arrived at. The corpus now answers
  this symptom four ways and none of them is this one. So the corpus routes the
  caller who lands on it past the mechanism rather than leaves it without an
  answer.
- Not `high`. One session reported it once, and the gap is a statement rather
  than a capability.
- A hint of its own, curated on where the site came from rather than on the 404.
  `site-base-collision` already holds the root-404 phrases, and a second hint
  curated on those is the competition `D-KNW-092` and `D-KNW-097` each paid to
  avoid. What this session could not answer was the provenance: a site nobody
  wrote, named `autogenerated-`, with the root page's slug reset under it.
- In `knowledge/hints/project.json` beside that cluster rather than in
  `datahandler.json`. The caller arrives with an installation that does not
  answer, not with a question about `DataHandler`.
- The neighbour lines are part of the work rather than after it. A fifth cause
  nothing points at is in reach only for the caller who already knows its name.
  Both the skill sentence and the `installation-operations` intent enumerate the
  other four.
- Neither archived nor trimmed. No part of the mechanism is stated anywhere
  today, and the routing half moved to a different wrong neighbour rather than
  to the right one.

## Assumed

- That this hook wrote the site the session that reported found. This run read
  the class and the identifier format it produces. The installation is in
  somebody else's checkout and nothing here can reach it.
- That `t3g/blog` extends `$allowedPageTypes` with a registered subclass. The
  feedback says so, the registration key makes it the available route, and no
  checkout here holds that extension.
- That the statement holds unbound. The class and its registration are on all
  four checkouts, and this run read the identifier, the base and the slug reset
  on `14.3` alone. So it may need a bound the todo establishes.
- That a caller arrives on the provenance words rather than on the symptom. The
  measure is that the symptom words already have a claim on them. Which words
  the next session reaches for is not something this run can know.

## Wrong if

- `12.4` or `13.4` invent the identifier or the base differently, or reset the
  slug at another moment. The statement is version-bound and the third
  **Assumed** was the wrong way round.
- The hint lands and a provenance query still answers `site-label-language`
  first. The lever would have been that hint's own curation, and this is step 4
  of the ladder rather than step 1a.
- The hint comes back on a plain root-404 query, or displaces
  `site-base-collision` on one. The boundary between the two would be wrong and
  the fifth cause belongs inside the collision hint after all.
- The next session with an autogenerated site reports that what it needed was
  how to correct the base rather than where the site came from. The gap would be
  in the procedure, and a statement of provenance would not have closed it.
- An extension turns out to reach `$allowedPageTypes` some other way — an event,
  a configuration key, a doktype registration that carries it. The half that
  explains why a custom root page got a site at all would be wrong.
- A caller follows the statement, finds the base is a sub-path, and corrects it
  into a collision with a site that already names the host. The two hints would
  owe each other more than a neighbour line.

## Confirmed on 2026-08-18

The hint stands and the first **Wrong if** does not hold. The class is the same
on all four checkouts, down to the identifier, the base and the slug update
after the write. Two differences were read and neither reaches a caller, so the
statement is unbound and the writing class is left unnamed — the diagnosis is
the identifier and the base.

What the hook leaves behind is a single-language site with no error handler at
all. The hint states two things beside it for the same reason. The hook skips a
root page that already has a site, and a failed write is a flash message rather
than an exception. The registration route holds as read, and the fifth **Wrong
if** stays open. What the run verified is that this route works. The three
routing measurements were re-run and the boundary is where it was drawn.
