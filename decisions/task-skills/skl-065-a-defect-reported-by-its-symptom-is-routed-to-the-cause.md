# D-SKL-065 — A defect reported by its symptom is routed to the cause

**A diagnosis of a broken installation earns a route rather than a skill of its
own. The half of it that has an order already has one published.**

Three tasks of one benchmark asked for the file and the cause with nothing
changed yet, and no published description covers that shape. Measured against
the server, what fails is the brief that answers such a request rather than the
absence of a workflow behind it.

## Evidence

- **The shape, as it stands on record.** `D-SKL-033` reads a benchmark outside
  this repository on 2026-08-19: seventeen project tasks, twelve skills listed
  and none loaded. Three of the seventeen were a page that answered with an
  error or rendered the wrong thing. The request was the file and the cause with
  nothing changed yet. The count and the shape are what is on record here; the
  prompts are not.
- **The half that has an order has it published.**
  `typo3-development-installation`'s **The installation that already answers**
  reads what the installation wrote down first. It treats an empty log as a
  finding rather than as an absent file, and fetches the rendered page only
  where the installation wrote nothing. It routes from the line it carries to
  `page-not-found-within-a-site`, `installation-boot`, `site-base-collision`,
  `autogenerated-site-configuration`, `project-configuration-files` and
  `typo3_configuration_lookup`. `D-SKL-059` is what put that there.
- **The knowledge under it is the expensive half and it exists.**
  `installation-exception-output` states where an uncaught exception lands, and
  that the name of the file is an HMAC, found as `var/log/typo3_*.log`. It
  states which codes the page displays and never writes at all. It states that
  `SYS/displayErrors` with the mask behind it decides whether the page carries
  the message.
- **What remains of the other half is one call and the caller's own checkout.**
  Once the symptom sits in a subsystem, every step after that is a read of files
  this server says three times it does not read. Those are the git state, PHP
  source as code, and the content itself. So there is no second order to write.
- **The placement call answers, and answers on a miss too.** Run against this
  checkout on 2026-08-19. `typo3_hint_lookup` with "the frontend page answers
  with an error and I need to find which file causes it" matches nothing. It
  returns the index closest first, with `installation-exception-output` at the
  top of it. `bin/cli hints:probe` reaches `content-elements` from a content
  element that renders wrong. It reaches `datahandler-relations` from a field
  that does not save, and `caching` from a page that serves the old content.
- **What fails is the route, and it fails towards writing.** Three
  `typo3_task_guide` calls, same day, same checkout, over stdio. "A content
  element renders the wrong markup on the page, find the cause" gets the
  content-element intent and hands over `typo3-content-element-development`.
  "The backend module shows a blank page since the upgrade, find out why and
  report the file and the cause, change nothing" hands over
  `typo3-backend-module-development`. "The frontend page answers with an error
  and I need to find which file causes it, without changing anything" gets no
  recognition at all. It matches no hint. It comes back with the checklist for a
  patch: keep it focused, add the narrowest useful coverage, draft the commit
  message.
- **The right answer is reachable only by naming it.** The same 500 task with
  `changeType="operations"` stated by the caller hands over
  `typo3-development-installation` and carries `installation-exception-output`
  with it. That argument is the answer the diagnosis is looking for.
- **The listing has no room for a fourteenth description.** The thirteen
  published ones cost 3966 characters against the 3970
  `SkillTest::everyDescriptionIsWrittenToALengthOfItsOwn` allows, measured on
  2026-08-19 with that test's own arithmetic.

## Decided

- **No skill for the shape.** The installation half is a published workflow. The
  other half is one lookup and then a read of the caller's own files. That is
  not an order anybody can get wrong in a way a skill would fix.
- **What it earns instead is an intent that changes nothing**, in
  `knowledge/task-intents.json`, plus the no-write brief behind it. That is the
  fourth after `audit`, `triage` and `installation-operations`. `TaskGuide`
  forks its skeleton on exactly that property today. So a request that asks for
  a cause no longer gets the steps a patch owes.
- **Queued rather than built here.** A session measures the needles against the
  corpus and against the cases that must miss from now on (`D-SKL-011`,
  `D-SKL-039`). That is a change of its own. This entry is the read that says it
  is the repair.
- **The case exists before any of it.** `SKILL-15` carries the prompt at
  contract `open`. `D-SKL-035` charges a new domain a run without the skill;
  this entry declines the domain, so what the case measures is the route.
- **Rejected: a wider published description.** Only
  `typo3-development-installation` is close, and it would have to name a content
  element that renders wrong. That is a side its body does not own, which is the
  failure `SkillTest::aBackendPreviewTaskMatchesTheSkillThatOwnsTheElement`
  exists for. Four characters of listing are what remains for it anyway.

## Assumed

- That the three benchmark tasks are the shape the todo describes. The benchmark
  is outside this repository, so the count and the shape come from `D-SKL-033`
  and from the todo rather than from the prompts.
- That a diagnosis divides into those two halves. It is a read of what the tools
  and the corpus answer, not of a recorded session that did one.
- That the cause of such a defect is inside TYPO3. A page broken by the web
  server, the container or the deployment is the same request with none of these
  answers behind it. Nothing here has measured how often that is the case.

## Wrong if

- A session with the intent in place still hand-reads its way to the cause and
  reaches neither half's owner. Then the route was not the obstacle, and the gap
  is an order after all.
- A run of `SKILL-15` names a file and a cause that neither the installation
  half nor a subsystem hint could reach. Then the shape is wider than this entry
  read it.
- A second reported shape arrives where the work after the placement call is
  long enough to have steps of its own. Say a trace of a value through the
  project's own PHP, which `SKILL-09` already shows a review get wrong. Then the
  leftover is a workflow and this entry called it a lookup.
- The no-write brief exists and a diagnosis request still comes back with the
  patch checklist, because the guide recognized it by its subject first. Then
  the fork is in the wrong place and the intent alone does not reach it.

## Since then

The intent landed as `diagnosis`. What settled the needles is that two words
carry the shape and no sentence needs an enumeration. They reach all three
measured calls and the contract case, and across the scenario prompts and the
one-kind briefs neither reaches anything else. One more is in because it is the
other word a caller asks the question with. Two are in as the change type, for
the reason `triage` exists. One phrase got a measure and a rejection, because it
reaches a review.

The entry names no skill, and the needles are why. The same two words reach a
content element that renders wrong and an installation that answers wrong. So an
unconditional route would hand the first the workflow that boots something. The
other cost stands stated rather than guarded. A request that names a cause and a
fix in one sentence gets a diagnosis unless the caller states the type.
