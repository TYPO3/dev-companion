# Nothing says how a site answers a 404 with a page of its own

## Observation

Task: audit the pages of a project site on TYPO3 v14 and fix what is broken. One finding was that config/sites/main/config.yaml carried an empty errorHandling, so a wrong address answered with the core's bare English "Page Not Found" document instead of a page of the site.

I called typo3_hint_lookup with id=page-not-found-within-a-site, expecting the configuration to be there. That hint is excellent at what it does - it reads the reason line to tell a routed-and-withheld page from a page that does not exist, and the sentence-with-exclamation-mark distinction is the sort of thing nobody derives alone. But it is entirely diagnostic. It even says that a site which does configure a handler answers with the configured page and drops the message, which names the configuration as the thing that changes the outcome and then does not say what that configuration looks like.

So the whole repair - errorCode, errorHandler: Page, errorContentSource as a t3://page?uid= reference, and the fact that the response keeps status 404 - came from memory, with no way to confirm it against the server for v14. The neighbouring case I also weighed, answering a not-found from inside a data processor when a record-detail argument resolves to nothing, is not covered either; ErrorController plus PropagateResponseException is the shape I know from core and nothing here confirms it.

The available-hints index has no entry for site error handling at all. The closest, autogenerated-site-configuration, is about what the core writes for a new root page.

What would have helped: a hint on the answering side, reachable from "404 page", "error handling", "errorHandling" and "not found page" - the errorHandling entries a site configuration takes, the three handler kinds, that errorContentSource is a link reference and what a wrong one costs, that the status code stays what the code says while the body comes from the page, and the two facts that bite: the error page has to be reachable for the internal subrequest, and a page hidden from the menu is the usual shape for it. page-not-found-within-a-site should link to it, since it already names the configuration as the discriminator.
