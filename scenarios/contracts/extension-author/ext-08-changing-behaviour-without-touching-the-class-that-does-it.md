# EXT-08 — Changing behaviour without touching the class that does it

**Environment:** `E-EXT` · **Contract:** `held`
**Held by:** `KnowledgeTest::aBriefNamingOneKindOfWorkConfirmsThatKindAndNoOther`
and `KnowledgeTest::everyKindOfWorkHasSuchABrief`, which hold that a task naming
this work reaches the `event-listener` intent and no other, and
`HintsTest::survivingHooksAreNamedByTheirSubsystemAndIntent` for the hook half
the hint sends back to its subsystem.
`ScenariosTest::aCasesOwnPromptConfirmsTheIntentItIsWrittenAbout` holds the same
of the words below, which is what the two briefs above cannot. That a session
checks the event is dispatched before writing a listener for it is **not
guarded**, and this case measures it.

**Read 2026-09-02:** the `event-listener` intent still opens on the check this
case measures — find the event that is really dispatched before writing a
listener for it, because one bound to an event nothing dispatches never runs and
raises nothing. Repaired on 2026-08-19: the prompt below reached nothing, so the
goal became three needles of its own — `without overriding`,
`instead of overriding`, `do not want to override` — and the prompt confirms the
intent since (`D-GUI-015`).

> Our extension has to add a line to the mail that the core sends after a
> registration. I do not want to override the class that sends it.

**What the agent needs from this server**

- Which registration mechanism this TYPO3 line has, and that a package serving
  two majors needs both.
- What an event class owes its listeners, and what ordering is declared with.
- That a hook is a fact about a subsystem rather than the fallback when no event
  is found.

**What has to come out of it**

- The event that is actually dispatched is established from the installation or
  the checkout before a listener is written against it. A listener bound to an
  event nothing dispatches never runs and raises nothing, which is this task
  shape's failure instead of an error.
- The registration is the one the covered line has, with the range it holds on.
  The attribute and the service tag are two mechanisms and the answer says which
  majors each is for.
- Where the listener's result depends on another listener having run, that is
  declared rather than assumed.

**How it fails**

- A listener registered by the mechanism the agent knows, unbound, so the
  package breaks on the other major it claims.
- The class that sends the mail overridden through XCLASS or a copy, which is
  what the prompt asked not to do.
- An event class invented because none was found, and the work reported done.
