# SITE-09 — One more setting in the site package's set

**Environment:** `E-SITE` · **Contract:** `held`
**Held by:** `KnowledgeTest::aBriefNamingOneKindOfWorkConfirmsThatKindAndNoOther`
and `KnowledgeTest::everyKindOfWorkHasSuchABrief`, which hold that a task naming
this work reaches the `site-setting` intent and no other, and
`ScenariosTest::aCasesOwnPromptConfirmsTheIntentItIsWrittenAbout`, which holds
the same of the prompt below. That a session then puts the definition and the
value in the different places the brief names is **not guarded**, and this case
is what measures it.

**Read 2026-09-02:** the `site-setting` intent still separates the two places
this case is written about — the definition with its type, default and label
belongs to the set that owns it, and the value belongs to the site's own
configuration — and still says which line has sets at all. Repaired on
2026-08-19: the prompt below detected the intent weakly and confirmed nothing,
so `add a setting`, `add the setting` and `per site` became needles of it and
the prompt confirms it since (`D-GUI-015`).

> Our editors want to switch the footer's copyright line per site without a
> deploy. We already have a site package with a set. Add the setting.

**What the agent needs from this server**

- What a site set is, and that a setting is defined in one place and given a
  value in another.
- Which sets this project's sites already depend on, rather than a set invented
  beside the ones that exist.
- The boundary where the site configuration's own fields — languages, base,
  error handling — are not covered.

**What has to come out of it**

- The definition and the value are separate steps, and the answer says which
  file each belongs in. A default written once and never overridden is the shape
  that makes the whole mechanism pointless, and the brief says so.
- The set that owns the setting is named, and why it is that one. A package with
  several sets has to answer this and a package with one still gets asked.
- A TypoScript constant is not offered as the way to do it, and the reason is
  the version rather than taste: sets arrived in TYPO3 v13 and
  `settings.definitions.yaml` replaced constants there. A package that still
  serves v12 has no set to define one in, so the answer says which line it holds
  for instead of stating one mechanism for all of them.
- Where the package still has constants, moving them is a separate task with its
  own hint, and this one does not do it on the way past.

**How it fails**

- A constant added to `constants.typoscript` because that is what the existing
  package does, with nothing saying a setting is what this line has instead.
- The opposite failure: a set setting prescribed to a package whose supported
  line has no sets at all, which is the same mistake pointed the other way.
- The site configuration file edited for a value that belongs to the set.
- A setting defined with no type and no default, so nothing tells an integrator
  what may be written into it.
