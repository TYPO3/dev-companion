# What a registration file resolves to, beyond the identifiers it names

The identifier half is done since 2026-09-02: `typo3_backend_module_lookup`
takes a `file` and says which `parent` and which `iconIdentifier` it names that
this installation does not have, without a cache flush and without the file
being installed. The file is read as text and nothing in it is executed, so a
value a constant or a variable computes is reported as unread rather than
followed.

Two things are left and neither is queued as work yet.

The labels domain is read and not resolved. A domain resolves once the module is
registered, which is the state this call exists to precede, so what a check
would need is the XLF file behind the domain rather than the registry. Nothing
here computes that direction today — `TranslationDomain` goes from a path to a
domain and not back.

The resolution half — the route path per entry, whether an entry gets routes at
all, where it lands among its siblings — waits on the question `D-FBK-055` put:
it re-implements what `ModuleRegistry` does, and two answers about where a
module lands is worse than one that needs a cache flush. What would settle it is
a session reporting a placement mistake the hints written the same day did not
prevent.
