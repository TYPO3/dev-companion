# Write the procedure for proving a rendering over HTTP

Judged on 2026-09-04 and trimmed to this half — `D-ANS-150` carries the
judgement. The scope half is done: every guide an answer names says which kind
of work it is for, so a caller stops parsing the first segment of the id. The
re-filing the feedback asked for was refused with the page as evidence:
`core/testing/proving-a-rendering` writes a functional test into
`typo3/sysext/frontend/Tests/Functional/Rendering/` and reads the core's own
autoload and PHPUnit configuration, so `core/` is right and the session skipped

What is left is the document that was actually missing. **Proving a rendering in
an installation you can request over HTTP** — the procedure the reporting
session worked out from scratch, which nothing here carries:

- choose the URLs to capture from the content that exists rather than from what
  the templates allow: which pages carry which CType, which is now one
  `typo3_record_lookup` call with `groupBy` and the rows departing from a default
- capture them before the change, make the change, capture them again
- what has to be run between the two so the second capture is the new rendering
  rather than a cached one
- read the diff at all: the session inserted a newline between adjacent tags
  first, and then grepped the union of every diff for a line none of the
  intended changes explains, which is what proved nothing else moved

It goes to `knowledge/documents/any/testing/`, beside `any/testing/browser-check`
and `any/testing/proving-a-condition`. First step is the reading this judgement
did not do: what the commands between the two captures actually are on a
Composer installation, verified rather than recalled — the session names
