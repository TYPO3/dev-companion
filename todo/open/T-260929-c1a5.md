# Read changelog identifiers from the listing, not from classes.json

docs.typo3.org renders the field since render-guides#1464. On 2026-10-28, 283 of
the 459 entries in `Changelog-14.json` carried `classes`. Each class maps to a
list of occurrences, each with a `section` and a `kind`.

Since render-guides#1464, each entry in `Changelog-<major>.json` lists the PHP
classes it names, with their members. `CoreChangelog::major()` reads that
listing already. So the identifiers of a manual entry become a field that
`listed()` reads, and the third read is gone. That read is `identifiers()`, the
`$classes` static and `indexed()`.

- `listed()` gives each entry its identifiers. Each class, with each of its
  `members`, goes through `Changelog::named()` as one inline literal, the way
  `indexed()` does it today.
- `ChangelogLookup` takes the identifiers from the entry. `UNINDEXED` and the
  two notes that name a missing class index go. A listing that came in carries
  the classes, and a listing that did not come in already has a note.
- The `member` fallback in `indexed()` goes with `indexed()`.
- The four `D-ANS-168` tests move to the listing.
  `aQueryTheNamesAnswerReadsNoClassIndex` and
  `aMissingClassIndexIsNamedInTheAnswer` hold nothing afterwards, so they go.
  `D-ANS-168` gets a successor that says the listing is the source.
- The tool description and
  `documentation/server/tools/typo3_changelog_lookup.rst` name the class index.
  Reread both.

Before the change, measure the listing against the index: do the classes of all
entries give the same identifiers per page that `classes.json` gives? Where they
do not, the difference goes into the successor's evidence.
