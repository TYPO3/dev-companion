# a record for one client hides the absent skills from another

Step 2 of the ladder: `Installer::ABSENT` exists, and the record of a different
client kept it from the session. `D-DIS-034` holds the judgement. The priority
is `normal` because the failure is silent: the session got no workflow, and
nothing told it so.

**Established on 2026-10-28**, from logged handshakes in a scratch project:

- Claude Code 2.1.312 sends `clientInfo.name` `claude-code`. It opens with
  `server/discover` at protocol `2026-07-28` and carries the name in
  `_meta["io.modelcontextprotocol/clientInfo"]`.
- Against this server it sends no `initialize` at all: `server/discover`, then
  the three lists. Only against a server that fails the probe does it fall back
  to `initialize`, with the same name in `params.clientInfo`.
- mcp/sdk v0.9.0 answers `server/discover` in `StatelessProtocol::answer()`
  from `Configuration::$instructions`, before the request handlers. The
  `InitializeHandler` path is the only one a handler of this server's own can
  replace, and custom handlers come first there.
- A `codex exec` run with this server in its configuration wrote no line to the
  server in 120 seconds. Codex's name is not established. Nor is any other
  client's in `Installer::AGENTS`.

What to build, once the question in the head has its answer: map an established
name to its key in `Installer::AGENTS`. The client has its skills where a
recorded client publishes to the same skills directory. Where none does, the
instructions open with `ABSENT` in place of the start notice. A name nobody has
established keeps today's answer. `D-DIS-034` names the two tests that hold the
instructions today.

The race the feedback reports first is outside this todo. Instructions that do
not arrive carry no sentence, and the maintainer answered that by keeping the
skill files and `install`.
